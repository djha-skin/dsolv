This article describes the overarching architecture of dsolv, together with some explanation about some of the design decisions. dsolv is a port of the degasolv dependency resolver from Clojure to Common Lisp; the architecture described here is inherited from degasolv.

Background

At one of my previous jobs, I was a Build Engineer — a person who built the code that the developers wrote and made it available. I had lots of dependency problems coming at me from all different sides:

  • One module in language A depending on another from language B
  • Developers working with a language (at the time) with no clear package manager ecosystem (**cough** C++ **cough**)
  • Package manager developers breaking builds with backwards-incompatible behavior
  • A dependency graph that looked like a dream catcher

So I decided to build a tool that would do these things:

  • Resolve dependencies the right way, safely
  • Even resolve dependency chains for different package systems (apt, pip, java)
  • Be super versatile and generic, able to be plugged into an arbitrary build script

Core Resolver

At the core of dsolv is a monster function called resolve-dependencies-deluxe. It is a rather large function with a backtracking, SAT-solver-ish design. Originally it was written to have a conflict strategy of exclusive and a resolve strategy of thorough hard-coded. In other words, the "first class" original use case of dsolv was a SAT-solver-class dependency resolver that only allowed a single version of any dependency, and ensured that all parties depending on that dependency had a chance to agree on what was chosen. These options were later added to allow dsolv to act more like Maven and give any build engineer using dsolv useful "handbrakes" to change how resolution was being done in-house so that it could be modified to conform to business needs. Other options, such as the list strategy and the search strategy, were added as time progressed as well for similar reasons, and also, frankly, to fix bugs (behaviors that were never originally intended).

dsolv models a dependency resolution problem with three main data structures, all built on FSet persistent data structures:

version-predicate
A relation (such as greater-than or less-equal) paired with a version string.
requirement
A status (present or absent), a package id, and a set of alternative version predicates (the "spec").
package-info
A package id, version, location, and requirements, as read from a card or a repository index.

Requirements are parsed from strings such as a>2.0,<3.0;>4.0 or !b by string-to-requirement.

Package Systems

dsolv resolves dependencies from "package systems" that know how to slurp repositories into query functions:

degasolv
The default package system. Reads .dscard files and .dsrepo repository indexes, using NRDL as the data format.
apt
Slurps Debian-style Packages.gz indexes. The parser deliberately avoids regular expressions: records are cut at blank lines and key/value pairs are split at the first colon using simple linear string operations. Regular expressions can be NP-hard to parse and made the original degasolv take about 40 minutes on the full Ubuntu package listing, so the parsing here is kept linear and predictable.
git
A stub, preserved for compatibility with degasolv's package system interface. It returns no packages.
subproc
Runs an external executable, parses its JSON or NRDL output, and converts it into resolver query functions. Configure it with -x/--subproc-exe and -u/--subproc-output-format.

CLI and Configuration

The command line interface is built with CLIFF. CLIFF gathers options from configuration files (NRDL or JSON), environment variables, and the command line, merging them into a single options table. dsolv adds degasolv-compatible command line aliases and DEGASOLV_* environment variable aliases on top of CLIFF's own conventions; see the Command Reference for details.
